# Synthetic input findings (2026-09-06)

## TL;DR: the "no reliable synthetic input" wall was a tooling-choice problem, not a real wall — same shape as the earlier screenshot fix.

`xdotool` fails here by *design*, not by accident: it relies on the X11 XTest extension, which Wayland's security model deliberately does not expose. Every prior attempt in this project used xdotool and concluded "synthetic input doesn't work on this machine" — that conclusion is too broad. **`ydotool` (kernel `uinput`-based, compositor-agnostic) works correctly against real GTK4 apps on this session, for both keyboard and mouse, verified visually, not just by exit code.**

## Setup (no root/group changes needed)

- `ydotool` and `ydotoold` are both already installed.
- `/dev/uinput` already has an ACL granting `user:<you>:rw-` (`getfacl /dev/uinput`) — no sudo, no group membership change needed. This machine was already set up for this; nobody had tried it.
- There is no systemd unit for `ydotoold` — it must be started manually per session: `ydotoold --socket-path=/tmp/.ydotool_socket &`. (The plain default invocation with no `--socket-path` did NOT create a socket in testing — always pass it explicitly.)
- Then: `YDOTOOL_SOCKET=/tmp/.ydotool_socket ydotool <command>`.

## What was verified, with real evidence (not just exit codes)

Target: `poc/neovide_embed_live` (real `nvim --embed` in a `GtkGLArea`), screenshotted via `poc/tools/screenshot.py` before/after each step and actually Read/inspected.

1. **Keyboard, minimal**: `ydotool key 23:1 23:0` (KEY_I down/up) against nvim's LazyVim-style dashboard, which was sitting at "Press ENTER or type command to continue". The message changed to **"E21: Cannot make changes, 'modifiable' is off"** — nvim's real response to an edit attempt on a read-only buffer. This is a distinct, causally-connected state change that can only happen if the keystroke genuinely reached nvim and was interpreted as a real edit command.
2. **Keyboard, full text entry**: `ydotool type "hello from ydotool synthetic input"` after `:enew<CR>` + `i` into a fresh editable buffer. Screenshot shows the buffer's line 1 reading exactly `hello from ydotool synthetic input`, cursor at the end. Character-perfect, no drops, no reordering.
3. **Mouse**: `ydotool mousemove -a -x 900 -y 300` then `ydotool click 0x00` (left click) while that text line was on screen, then typed a marker (`MOUSECLICK`) via keyboard. Result: `hello from ydotool synthetic inpuMOUSECLICKt` — the marker landed mid-word, proving the click was delivered to the window AND mapped to a specific, sensible character position (not a no-op, not landing somewhere random/off-window).

No orphaned `nvim --embed` processes after killing the test binary (`pgrep -af "nvim --embed"` afterward showed only the two pre-existing, unrelated long-running user nvim sessions).

## What this does NOT yet establish (be honest about the gap)

- **Absolute-position calibration attempted 2026-09-06 — result: `ydotool mousemove -a` does not reliably work on this system, not just "needs a scale factor".** Method: opened a real nvim buffer with a 71-character ruler line (`0123456789A...F123456789G`), clicked at two very different absolute coordinates (`-a -x 900 -y 300` and `-a -x 100 -y 300`), and revealed the landing column each time by entering insert mode and typing a distinct marker (`|MARK1|`, `|MARK2|`) — the same rigor as the keyboard/mouse proof above, not just checking exit codes. **Both landed at the identical position** (immediately before the last character of the line) despite the requested x differing by 800. This isn't an imprecise linear mapping that a scale/offset formula could fix — it looks like absolute positioning is clamping or otherwise not functioning as documented against this compositor (ydotool's own `--help` warns "you need to disable mouse speed acceleration for correct absolute movement," suggesting the compositor's pointer-acceleration pipeline may be interfering with what's supposed to be a direct absolute jump). Also tried: an automated pixel-diff approach (Python/PIL comparing before/after screenshots) to locate the exact landing pixel without relying on visual reading — this was defeated by frame-to-frame GPU rendering/anti-aliasing noise across the whole window, not just the changed text, so direct visual reading of the marker's position (as used throughout this document) is currently the more reliable verification method for this kind of test, not a fallback of last resort.
  - **Practical implication for P3/precise click targeting**: don't rely on `ydotool mousemove -a`. Relative movement (`ydotool mousemove -w -- dx dy` for wheel, or `mousemove -- dx dy` for pointer motion) is confirmed working (used successfully elsewhere in this session). A driving script needs to track cumulative position itself (ydotool has no "query current pointer position" command) and move in relative deltas from a known reference (e.g., click something with a known screen location first via keyboard-driven navigation, not a blind absolute coordinate jump).
  - Next step for whoever picks this up: investigate whether Mutter's pointer-acceleration setting can be disabled session-wide (`gsettings set org.gnome.desktop.peripherals.mouse accel-profile flat` or similar) to see if that's actually the root cause, before concluding absolute positioning is unfixable here.
- **IME composition was not tested at all this session** — ydotool's `type`/`key` deal in raw keysyms/Unicode codepoints, not IME candidate-window interaction. Whether pinyin composition (P4's actual concern) can be driven this way, or whether it needs a different mechanism (e.g. driving fcitx5/ibus directly via their own D-Bus interfaces, analogous to how gnome-shell's Screenshot vs. portal Screenshot are two different paths to a similar-looking capability) is unknown and should be the next thing checked before assuming P4 is unblocked too.
- **`org.freedesktop.portal.RemoteDesktop` was introspected but not exercised** — its `CreateSession`/`SelectDevices`/`Start`/`Notify*` methods are real and present, but `ydotool` already worked and is architecturally simpler (no session/handshake state, no portal-consent-dialog risk to figure out), so it wasn't necessary to pursue further this session. Worth knowing it's there as a fallback if `ydotool` ever turns out to have a gap RemoteDesktop's higher-level (IME-aware?) API doesn't.
- `wtype` is not installed and Mutter's `virtual-keyboard-unstable-v1` support wasn't checked — moot since `ydotool` already works and additionally covers mouse (wtype is keyboard-only).

## First real P3 automation pass (2026-09-06) — and a critical safety finding

**Confirmed working, visually verified each time (not just exit codes):**
- Multi-key chord sequences typed as plain characters: `gg` (go to first line), `dd` (delete line), `G` (go to last line), `p` (paste) run in sequence on a 3-line buffer produced exactly the expected reordering (ALPHA/BRAVO/CHARLIE → BRAVO/CHARLIE/ALPHA), confirmed via screenshot. `ydotool type` sending each character as a real keypress is enough for vim's normal-mode command parser to see them as real chords, not just literal insertion.
- Click-to-position: confirmed again (see the calibration section above) via the reveal-with-marker method — a real, working technique for verifying exactly where a click landed.

**`Ctrl+V` chord produced no observable effect — but this is expected, not a synthetic-input gap.** `poc/neovide_embed_live/MANUAL_VERIFICATION.md` item 9 documents that this crate's own key handler *deliberately* drops all Ctrl/Alt modifier chords (`src/main.rs`'s module doc calls full modifier-chord translation "a later, dedicated input-system phase, not this one's") — so "nothing happened" matches the crate's own documented current behavior. This test doesn't tell us whether `ydotool` can correctly deliver a held-modifier chord at the OS/compositor level at all; it only confirms this specific crate doesn't forward them yet (already known, not new information). Re-test modifier delivery itself against something that *does* handle Ctrl chords (e.g. a plain GTK app, or nvim's own terminal mode) before concluding anything about `ydotool`'s modifier support specifically.

**CRITICAL SAFETY FINDING (separate incident, later in the same session) — verify window focus with a screenshot before sending consequential keys, especially Escape.** While attempting to recover to a known state after the `Ctrl+V` test (a plain double-Escape, expected to just ensure normal mode), keyboard focus had silently moved away from the target `neovide_embed_live` window to **the controlling terminal itself**, with no error or visible indication in the moment. That double-Escape landed on the terminal instead and triggered **Claude Code's own "Rewind" dialog** (a real feature that can restore code/conversation to an earlier point) — caught and cancelled immediately via two more Escapes before anything was selected/confirmed; verified via screenshot that it returned to a normal empty prompt, no actual rewind occurred.
- **This is now a first-class operating rule for any future synthetic-input automation in this project, not just a caveat**: screenshot and visually confirm which window/app currently has focus before sending anything that could have consequences outside the intended target app — a misdirected keystroke isn't just a failed test, it can trigger real actions in whatever unrelated application happens to have focus. This is especially true for Escape (a common global shortcut in many apps, including the terminal this is normally driven from) and modifier chords.
- Root cause of the focus shift itself was not determined this session (possibly triggered by a `kill` command's process-exit side effects on window management, or something else) — worth investigating before doing more P3 automation, but the immediate risk is handled by the screenshot-first discipline above regardless of root cause.

**Not attempted this session, still open**: mouse drag-selection (blocked on the absolute-positioning failure above — a drag needs reliable start/end coordinates), wheel-scroll's actual effect on nvim's viewport (wheel events were confirmed *delivered* in the P6 re-run work above, but not confirmed to actually scroll nvim's buffer), and focus routing between `shell_composed`'s three panes (chrome/editor/WebView) specifically — the safety incident above happened before this could be tested and using the remaining time to fix the safety issue took priority over continuing further automation.

## Sandbox-native tools (`wtype`/`wlrctl`) instead of `ydotool` — findings, 2026-09-06 follow-up

Following the earlier safety fix (see the headless-sway sandbox), this pass re-did P3 testing using `wtype`/`wlrctl` (protocol-scoped, addressed to the sandbox's own `WAYLAND_DISPLAY`) instead of `ydotool` (global uinput injection against the real desktop). Both crates confirmed rendering correctly in the sandbox (`poc/neovide_embed_live`, `poc/shell_composed` — no `xdg-desktop-portal-gnome` needed for WebKitGTK to work here).

### Real, reproducible gaps found in the sandbox toolchain itself (not this project's code)

1. **`wtype`'s first character(s) can be dropped**, reproducibly, at the start of a plain `wtype "text"` call — e.g. `wtype ":e /path/to/file" -k Return` sent right after other input activity resulted in the leading `:` being lost, so `e /path/to/file` ran as bare Normal-mode commands instead (`e` = word-end motion, then `/path...` became a search pattern, producing `E486: Pattern not found: ...`). Reproduced multiple times across separate process launches, not a one-off. **Workaround**: prepend a short throwaway keystroke before the real payload, or add an explicit `-s <ms>` pause before the real content starts.
2. **`wtype -k <Key>` (tap: instant press+release) is unreliable for named/special keys** -- `wtype -k Escape` and even a modifier chord via `-M ctrl -k bracketleft -m ctrl` repeatedly failed to register (buffer stayed in `-- INSERT --`, confirmed via screenshot). **Reliable workaround**: separate press/release with an explicit gap -- `wtype -s 200 -P Escape -s 100 -p Escape` -- consistently worked. Use this pattern for any named key (Escape/Return/Tab/arrows), not `-k` alone, in future automation.
3. **`wlrctl pointer` has no absolute-positioning primitive at all** (unlike `ydotool`, which had one but it was broken) -- only `move <dx> <dy>` (relative), `click [button]`, `scroll <dy> <dx>`. Workaround confirmed reliable: move a large amount in one direction to clamp against a screen edge (e.g. `wlrctl pointer move -5000 -5000` to reach the top-left corner), then a precise relative offset from that known reference -- click landed exactly on the intended word in testing.
4. **`wlrctl pointer` has no separate press/release for buttons** -- only atomic `click`. This means **real click-and-drag (button held down while moving) is not achievable with current tooling** -- confirmed by checking `wlrctl`'s man page and its zsh completion definitions (`pointer` only exposes `click`/`move`/`scroll`, no press/release pair the way `keyboard` has `-P`/`-p`). This blocks automating: drag-selection in the editor, and dragging `shell_composed`'s `GtkPaned` divider handle. Would need either a lower-level custom Wayland client speaking `wlr-virtual-pointer-unstable-v1` directly (the protocol itself supports discrete button-state events; `wlrctl` just doesn't expose them), or a different/newer tool.

### What was confirmed working this pass

- **Focus-on-launch**: typing immediately after launch with zero prior clicks landed correctly in the editor (`gl_area.grab_focus()` on startup works as intended).
- **Click-to-position accuracy**: clamp-then-relative-move landed a click within the targeted word, confirmed via before/after screenshot -- this is a real, usable technique for precise click-target testing going forward (unlike `ydotool`'s broken absolute mode).
- **Focus isolation between panes**: clicking into `shell_composed`'s WebView pane, then typing, did not steal keyboard focus away from the editor -- input continued landing in the nvim buffer. Basic pane focus routing works correctly.
- **Ctrl/Alt modifier chords are correctly not translated** -- confirmed consistent with `neovide_embed_live`'s own module doc (`src/main.rs`): the keyboard adapter forwards `gdk::Key::to_unicode()` plus a handful of named keys (Escape/Return/BackSpace/Tab) and explicitly treats any Ctrl/Alt/Super-held keypress as "not plain text, ignore" -- a documented non-goal, not a bug, and not something the sandbox or `wtype` could have changed either way.

### P4 (IME): a real, precise negative result -- not a tooling gap, a code gap

`fcitx5` is running on this machine (`GTK_IM_MODULE=fcitx`), so an IME engine is genuinely available in principle. But **neither `poc/neovide_embed_live` nor `poc/shell_composed` wires up `GtkIMContext` at all** -- their keyboard input path is `GtkEventControllerKey` forwarding `gdk::Key::to_unicode()` directly (see `neovide_embed_live/src/main.rs`'s own module doc), which is a completely separate mechanism from IME composition. This means **IME testing isn't blocked by environment or tooling (sandbox or real desktop) -- it's blocked by the current code never attaching an IME context to the input widget in the first place.** P4 needs real implementation work (wire up `GtkIMContext`, handle preedit/commit signals) before there's anything for a test -- sandboxed or not -- to exercise. ## `wlrctl`'s missing press/release gap is now closed: `poc/tools/wlr_vptr_drag` (2026-09-06, follow-up)

Item 4 above (`wlrctl pointer` has no press/release, only atomic `click` -- blocking all drag-and-drop testing) is fixed. New crate **`poc/tools/wlr_vptr_drag`** (workspace member, binary `wlr-vptr-drag`) is a minimal custom `wlr-virtual-pointer-unstable-v1` client built directly on `wayland-client` + `wayland-protocols-wlr`'s generated bindings (both already available on crates.io -- no hand-rolled protocol framing needed, no XML vendoring). It exposes what the protocol always supported but `wlrctl` didn't expose:

- **Absolute positioning** (`zwlr_virtual_pointer_v1.motion_absolute`) -- `wlrctl` only had relative `move`. Interpreted as raw pixel coordinates with `x_extent`/`y_extent` set to `--screen-w`/`--screen-h` (default `1280x720`, the wlroots headless backend's confirmed default single-output resolution) -- this is only pixel-accurate for a single-output layout with that output at `(0,0)`, which is exactly what this project's sandbox always is. Do not point this at a real multi-monitor desktop and expect the same math to hold (and don't point it at a real desktop at all -- see the safety rule below).
- **Separate press → move → release**, composed as a real drag: `motion_absolute` to the start point, `button` press, N stepped `motion_absolute` calls toward the end point (not a single teleport -- mirrors how real drag-threshold detection in GTK/GDK expects to see intermediate motion), a brief hold, then `button` release. Usage: `wlr-vptr-drag <x1> <y1> <x2> <y2> [--button left|right|middle] [--hold-ms N] [--steps N] [--screen-w W] [--screen-h H]`.
- **Hard-coded safety rule, not just a convention**: the binary refuses to run at all if `$WAYLAND_DISPLAY` is unset -- it will never silently fall back to a default/ambient socket. This exists specifically because of the ambient-injection incident earlier in this project (see the critical safety finding above) -- this tool structurally cannot be pointed at "whatever the default socket happens to be," only at whatever the caller explicitly names.

**Verified end-to-end against the actual real target this gap blocked**, not just protocol mechanics: in the isolated headless-sway sandbox, launched `poc/shell_composed` (window auto-tiled fullscreen to the sandbox's 1280x720 output), located the real `GtkPaned` handle's exact pixel position by sampling pixel colors from a `grim` screenshot (`python3`+`PIL`, boundary found at x≈759-763, matching the crate's `paned.set_position(760)` default), then ran `wlr-vptr-drag 761 400 950 400 --steps 15 --hold-ms 300 --screen-w 1280 --screen-h 720`. Before/after screenshots (`grim`) show the pane boundary visibly moved from ~x=760 to ~x=908, exposing more of the LazyVim menu bar that was previously clipped -- and `shell_composed`'s own agent-panel stats overlay logged a real `stall 118ms`, which only fires from `install_webview_resize_throttle`'s `paned.connect_notify_local("position", ...)` handler (see `poc/shell_composed/src/main.rs`) -- i.e. this went through the actual `GtkPaned::position` property change path, not a coincidental redraw. This is the first real, screenshot-verified click-and-drag in this project.

**One process-hygiene note for whoever runs sandboxed tests next**: this session found a stray orphaned `neovide_embed_live --clean` process still connected to a *newly created* sandbox socket instantly on startup -- almost certainly a leftover from a concurrent/prior agent session sharing this same machine's `/run/user/<uid>/` socket namespace (headless-sway sockets are **not** isolated per-agent, only isolated from the real desktop). Always `pgrep -af "target/debug"` and screenshot-inspect before trusting a "before" screenshot is actually clean, and when tearing down, kill your own compositor PID specifically (matched by which `wayland-N` socket it owns, e.g. via `ss -xlp` inode cross-reference) rather than `pkill -f "sway --config"` by command-line pattern -- that pattern matches *any* concurrently-running sandbox compositor, including another agent's still-in-use one.

Remaining limitation: only single-output, origin-at-(0,0) absolute positioning is implemented (sufficient for this project's sandbox); no scroll/axis support was added (not needed for this gap, `wlrctl pointer scroll` already covers that).

**Correction (2026-09-06): the "`wlrctl pointer scroll` already covers that" claim above turned out to be wrong.** A later same-day pass found `wlrctl pointer scroll` sends a raw `wl_pointer.axis` event with no `axis_source` at all, and this sandbox's GDK/Wayland path silently drops such an event entirely (the scroll handler was never invoked, at any magnitude). The real fix was a new tool built specifically to close this: `poc/tools/wlr_vptr_drag/src/scroll.rs` (binary `wlr-vptr-scroll`), a minimal `wlr-virtual-pointer-unstable-v1` client that sends a real `axis_source(Wheel)` + `axis(...)` + `frame()` sequence — exactly what a real scroll-wheel notch produces. With it, scroll was confirmed working end-to-end (bidirectional, reliable). See `docs/canonical/neovibe_feasibility_status.md`'s "P3 结论(续四)" section for the full finding.

## CRITICAL SAFETY FINDING (2026-09-08): overriding `WAYLAND_DISPLAY` alone is not sandbox isolation for IME testing

**A synthetic key sequence briefly reached the real desktop's live input method during otherwise-correctly-isolated sandbox testing.** This machine exports `GTK_IM_MODULE=fcitx` as a session-wide environment variable, which is *not* scoped by `WAYLAND_DISPLAY` — a GTK app launched with only `WAYLAND_DISPLAY` overridden to point at the sandbox compositor still finds and talks to the **real desktop's** fcitx5 daemon over the ordinary (unoverridden) D-Bus session bus, because fcitx5's IPC has nothing to do with which Wayland socket the client's *rendering* connects to. A synthetic `Ctrl+Space` sent as part of a chord-forwarding test reached the real fcitx5 and switched the user's own live input method — caught and reverted immediately (`fcitx5-remote -c`), independently re-confirmed clean afterward (real desktop's fcitx5 back on the user's normal `rime` input method, no stray process left running).

**The fix, now load-bearing for any future GUI sandbox session, not just this one:** isolating a GTK app for sandbox testing requires overriding **`WAYLAND_DISPLAY`, `DBUS_SESSION_BUS_ADDRESS` (or running under a fresh `dbus-run-session`, which this project's sandbox recipe already does for its own bus, but that alone doesn't stop fcitx5 specifically from falling back to the *real* session bus address if the app still inherits it — confirm `DBUS_SESSION_BUS_ADDRESS` is actually the sandbox's own, not just that `dbus-run-session` was used to launch something), and `DISPLAY`** (unset entirely — an X11 fallback path can bridge back to the real desktop the same way). This is a **third distinct isolation surface** beyond the two already documented in this project (`WAYLAND_DISPLAY` for compositor/rendering, synthetic-input tool choice for `ydotool`-vs-protocol-scoped) — any environment variable an app or a library it links (fcitx5's IM module, in this case) uses to *discover* a running service rather than to *render pixels* needs to be checked, not assumed covered by "I changed `WAYLAND_DISPLAY`." When in doubt, run under a genuinely fresh `dbus-run-session` **and** explicitly confirm (don't assume) that whatever IPC mechanism the thing under test uses for IME/clipboard/portal/etc. is actually bound to that fresh session, not silently falling back to the ambient one. Full incident record: `neovide-editor/MANUAL_VERIFICATION.md`, `shell/MANUAL_VERIFICATION.md`.
